# План 40. Устранение постоянного snapshot_stale

## Цель и входы

По требованиям свежести агента и preflight из разделов 5–6 `CODEX.md`
устранить ложную блокировку после коррекции часов ПК и при heartbeat,
пришедшем во время чтения preflight.

## Диагностика

- Heartbeat принимает расхождение captured_at с сервером до пяти минут;
  preflight требует возраст 0–30 секунд. Приём heartbeat сам по себе не
  означает готовность к публикации.
- `latest` сортировался по часам ПК (`captured_at`): старый снимок из будущего
  скрывал новые heartbeat после исправления часов.
- Время оценки фиксировалось до чтения БД, поэтому новый heartbeat мог
  ошибочно оказаться в будущем; при медленном чтении возраст занижался.
- Причина на работающих ПК пока не подтверждена: локальный Compose не запущен.

## Решения и инварианты

- Последний heartbeat выбирается по серверному `received_at`, затем по
  `captured_at` при одинаковом времени приёма.
- Время оценки берётся после чтения данных; явный `now` для тестов сохраняется.
- TTL по `captured_at` остаётся 30 секунд, расширение до пяти минут и
  подмена времени создания временем приёма запрещены.
- Будущее время получает отдельную причину `snapshot_clock_skew`; старая
  запись — `snapshot_stale`. Оба результата запрещают publish.
- Сообщение содержит UTC-время создания, приёма (если известно), проверки,
  возраст и лимит, а также действие для оператора.
- `ProcessSnapshot.received_at` — необязательное поле read model из уже
  существующей колонки БД. HTTP heartbeat не меняется.
- Добавляется индекс `(station_id, received_at, captured_at)` отдельной
  миграцией `6d9e2b4a8c10`, чтобы накопленная история heartbeat не замедляла
  новую сортировку; существующие данные и индекс captured_at сохраняются.

## Слои и проверки

- repository: выбор последнего heartbeat, чтение received_at;
- application: фиксация времени после IO;
- domain: объяснение stale/clock skew без ослабления safety gate;
- tests: восстановление после коррекции часов, stale при свежем приёме,
  heartbeat во время чтения, истечение TTL во время IO, границы TTL и
  сохранение process/drive blockers;
- полный backend suite и Ruff; реальный publish/TrueNAS не запускать.

После доставки исправления на хост Controller выполнить
`docker compose up -d --build backend`; entrypoint применяет миграции.
Дождаться нового heartbeat и нажать «Повторить проверку». При сохраняющейся
блокировке использовать показанные времена: свежее время приёма при старом
времени создания требует проверки часов ПК или задержки сбора/доставки;
старое время приёма — проверки службы агента и связи.
